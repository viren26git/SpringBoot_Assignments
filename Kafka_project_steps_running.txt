Also,
Now understand offset with our actual example
Suppose Kafka has:

order-events / Partition 0

Offset       Order
-------------------------
0            ORD-101
1            ORD-102
2            ORD-103

Inventory consumer reads:  ORD-101
then:
offset = 0

After successful processing, the group progresses.
Then: ORD-102
is processed.

Then: ORD-103

If Inventory crashes while processing ORD-103, the offset may not have been committed for that record.
After restart:
Inventory Service
       |
       v
Kafka
       |
       v
ORD-103

can be delivered again. Therefore your Inventory code should be safe if:

ORD-103 is processed twice.


This is why idempotent consumers are important

Imagine:

ORD-101

causes:

Inventory quantity = 10

Consumer receives order:

quantity = 2

and reserves:

10 - 2 = 8

If the same message is accidentally processed again:

8 - 2 = 6

That is WRONG.

Therefore, in a real Inventory Service, we need something like:

Processed Events
-------------------------
ORD-101
ORD-102

Before processing:

Is ORD-101 already processed?

If yes:

Ignore duplicate

This is consumer-side idempotency.
